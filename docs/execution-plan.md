# Execution plan

This plan preserves the product rule: coverage may increase only when provenance and comparison evidence remain defensible. Dates are target windows, not permission to bypass a gate.

## Current baseline — v0.1.0

Target: 2026-08-25 to 2026-08-27

Deliverables:

- Public source release at a green GitHub Actions commit.
- Three supported `EXACT` regression bundles and two explicit `UNSUPPORTED` counterexamples.
- Public brief, deterministic demo, independent-review protocol, and grant evidence.

Exit gate:

- Release tag points to a clean, remotely verified commit.
- No known path upgrades insufficient provenance into a supported replay.
- Release notes preserve all material limitations.

## External evaluation window

Target: 2026-08-28 to 2026-09-10

Work:

- Ask at least three independent Solana/runtime/security reviewers to run the published protocol.
- Triage findings by severity and publish reproducible fixes.
- Record reviews, including negative conclusions, with reviewer consent.
- Measure clean-install success and time-to-first-regression.

Exit gate:

- At least two independent reports are reproducible, or the absence of reviewers is recorded as an adoption gap.
- No unresolved critical false-positive or bundle-integrity finding.

## Phase 2 — Historical State Providers

Target: 2026-09-11 to 2026-10-08

Work:

- Publish a provider capability and conformance contract.
- Harden `FixtureProvider` and `SnapshotProvider` with immutable-source manifests.
- Add provider conformance tests for slot identity, source identity, missing history, and current-state rejection.
- Evaluate one archive-provider adapter without coupling the core to a vendor.

Exit gate:

- Every provider declares capabilities and evidence source explicitly.
- Provider failure or unavailable history returns `UNSUPPORTED`.
- No archive integration is merged without real historical-state validation.

## Phase 3 — Public benchmark

Target: 2026-10-09 to 2026-11-20

Work:

- Build a public corpus of approximately 100 real mainnet transactions.
- Publish per-case class, provider, provenance, runtime, result, structured reason, and replay duration.
- Report `EXACT`, `SEMANTIC_MATCH`, `PARTIAL`, and `UNSUPPORTED` separately.
- Preserve the denominator; never remove difficult cases to improve the support rate.

Exit gate:

- Corpus construction is reproducible and deduplicated.
- Every classification is machine-generated from explicit rules.
- Coverage claims name the corpus and never imply mainnet-wide support.

## Phase 4 — Portable distribution

Target: 2026-11-21 to 2026-12-18

Bundle v0.1 is already portable at the source/artifact level. This phase hardens distribution:

- Prebuilt CLI artifacts for Windows, Linux, and macOS where reproducible.
- Checksums, release provenance, and automated smoke tests.
- A stable bundle pack/verify workflow.
- A reusable GitHub Action for regression assertions.

Exit gate:

- Fresh machines can verify a bundle without compiling the native backend, or unsupported platforms are explicit.
- Release artifacts are generated by CI from a tagged commit.

## Phase 5 — Transaction-class expansion

Start: 2027-01; one class per release.

Proposed order:

1. Simple Token-2022 transfers.
2. Historical ALT fixtures.
3. Bounded simple CPI.
4. Upgradeable-program version capture.
5. Oracle-aware cases.
6. One named DeFi protocol at a time.

Support gate for every new class:

- A precise transaction classifier.
- Defensible pre-state and program provenance.
- At least ten real cases including failures/negative cases.
- Explicit comparator semantics and adversarial tests.
- Zero known false-positive reproductions.
- Documentation and independent review before the support claim ships.

## v1.0 gate

Version 1.0 is earned when the project has:

- a stable provider conformance contract;
- a public approximately 100-transaction benchmark;
- cross-platform release artifacts;
- a stable portable bundle contract with migration policy;
- at least two independent technical reviews;
- measured coverage with no universal-replay claim;
- a documented response process for incorrect `SUPPORTED` classifications.

## Metrics

Primary trust metric:

> Number of published real-mainnet cases with independently reproducible classifications and zero known false-positive `SUPPORTED` outcomes.

Supporting metrics:

- clean-install success rate;
- median time to reproduce a bundle;
- cases by fidelity class and reason code;
- provider capability coverage;
- independent reviews completed;
- regressions caught by CI artifacts.
